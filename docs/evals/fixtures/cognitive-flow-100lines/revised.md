# なぜレビューは遅れるのか——待ち時間を半分にした現場の記録

文書種別想定: 解説記事（ブログ）。評価時は `review`。

---

あるプロダクト開発組織で、プルリクエストのレビュー待ちが機能追加のリードタイムを伸ばしていました。レビュー待ちを減らすには、レビュー担当のローテーション、指摘テンプレート（`REVIEW.md`）の必須化、レビュー依頼から24時間以内の初回応答目標という三つの施策をセットで入れるのが効きます。今回のパイロットでは、レビュー初回応答の中央値が18時間から6時間、マージまでの中央値が2.4日から1.1日、差し戻し率が12%から5%に下がりました。インフラ増強ではなく、待ち時間そのものを設計対象にした点が転換点でした。

## 現場で起きていたこと

あるプロダクト開発組織では、機能追加のリードタイムが伸びていました。Backend グループ（12名）は、レビュー依頼から初回応答までの中央値が18時間、マージまでの中央値が2.4日、差し戻し率が12%という状態でした。障害が再発する可能性があるため、監視の強化が議論されていましたが、その前に「そもそもレビューが滞っている」という声が現場から上がっていました。

## 試したことの経緯

パイロットは2026年7月に実施しました。ローテーションを始めたのは7月15日です。その前の7月1日に、指摘テンプレート（`REVIEW.md`）を必須化しました。準備にはおおよそ2週間かかりました。もっとも効果が大きかったのは、レビュー依頼から24時間以内の初回応答を目標にしたことだ、という声もあります。時系列で整理するとテンプレートが先で、重要度で言えば期限設定が最初に来るべきだった、という振り返りがチーム内に残っています。7月31日にパイロット期間を終え、数値を集計しました。

Circuit Breaker パターンは、外部依存の障害を局所化する設計です。前述のレビュー改善とは別の話題ですが、信頼性の文脈ではよく引き合いに出されます。今回のパイロットでは通信経路の変更は行っておらず、外部 API 呼び出しは従来どおり HTTP ではなく HTTPS を使う方針を維持しています。

## 施策の中身

本施策により、レビューが効率化します。これは意思決定を速くするための取り組みです。

施策の本体は次の三つです。

1. レビュー担当を日次でローテーションする
2. 指摘テンプレート（`REVIEW.md`）を必須化する
3. レビュー依頼から24時間以内の初回応答を目標にする

ローテーションは属人化を減らすための仕組みです。テンプレートは指摘の粒度を揃え、差し戻しの理由を再利用しやすくします。24時間目標は、待ち時間の上限をチームの約束として可視化します。

## 計測結果

計測結果は次のとおりです。

- レビュー初回応答の中央値: 18時間 → 6時間
- マージまでの中央値: 2.4日 → 1.1日
- 差し戻し率: 12% → 5%

## おわりに

Platform チームは、2026年9月末までに他グループへの展開可否を判断する予定です。障害が再発する可能性があるため、監視ダッシュボードへのレビュー滞留アラート追加を推奨します。アラートの設定を保存すると、次回起動時に読み込まれます。必要に応じて手動で再読込もできます。
