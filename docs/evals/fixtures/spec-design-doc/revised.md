# レビュー滞留アラート機能 設計メモ

文書種別想定: 設計書・仕様書（社内）。評価時は `review`。リズム調整は弱。平坦さの〔助言〕は適用しない。

---

本機能の目的は、レビュー依頼後 24 時間（既定）を超えて初回応答が無い PR を Slack に通知し、滞留を早期に解消できるようにすることである。行為者はバッチジョブ `review-watch-worker`（毎時 0,15,30,45 分）であり、入力は GitHub open PR、出力は Slack 通知とダッシュボード上の滞留一覧である。前提は `REVIEW.md` の存在、GitHub App review-watch v1.4.0、所定の webhook である。対象外は下書き PR と `do-not-alert` ラベル付き PR である。

## 背景

Platform チームは、レビュー依頼から初回応答までの中央値が伸びると、機能追加のリードタイム全体が押し上がる、という仮説のもとで対策を検討している。

## 前提条件

対象リポジトリのルートに `REVIEW.md` が存在していること、GitHub App「review-watch」v1.4.0 がインストール済みであること、および Organization の webhook に `pull_request` と `pull_request_review` が含まれることが前提である。

## 処理の流れ

オペレータはダッシュボードを開き、滞留一覧を確認する。滞留と判断された PR は、Slack の `#eng-review` に通知される。通知先チャネルは環境変数 `ALERT_SLACK_CHANNEL` で上書きできる。タイムゾーンは `Asia/Tokyo` 固定とする。

処理は次の順序で行う。まず GitHub から open な PR を取得し、最終レビュー催促からの経過時間を計算するため、レビュー催促イベントを読む。経過時間が閾値（デフォルト 24 時間。`ALERT_THRESHOLD_HOURS` で変更できる）を超えていれば、Slack に投稿する。取得に失敗した場合は最大 3 回リトライし、それでも失敗したらエラーをログに出し、その PR をスキップする。

Circuit Breaker は外部 API 障害の局所化に使う。本機能の必須構成ではないが、信頼性の文脈では言及されることがある。外部 API 呼び出しは HTTP ではなく HTTPS を使う。

## 入出力の概要

入力は GitHub の PR 一覧である。出力は Slack メッセージである。誰が・どの条件で・何を出すかは、運用者がダッシュボードで確認する想定である。

滞留の定義は、レビュー依頼ラベル `needs-review` が付いたあと、初回の approve / request_changes / comment レビューが無く、かつ経過時間が閾値以上の PR とする。下書き PR と `do-not-alert` ラベル付き PR は対象外とする。

## 設定項目

- 閾値: `ALERT_THRESHOLD_HOURS`（整数、単位は時間、デフォルト 24）
- 通知先: `ALERT_SLACK_CHANNEL`（文字列、デフォルト `#eng-review`）
- ドライラン: `ALERT_DRY_RUN`（真偽、デフォルト false）。true のときは Slack 投稿を行わずログのみとする
- バッチ間隔: 15 分固定。設定では変更できない

## 例外と失敗時

GitHub API が 403 を返した場合は、権限不足としてジョブ全体を失敗させる。個別 PR の取得失敗は、上記のとおり最大 3 回リトライのあとスキップする。Slack API が失敗した場合は、その通知だけを失敗とし、他 PR の処理は継続する。障害が再発する可能性があるため、ジョブ失敗時は `#eng-platform` へのページャー連携を推奨する。
