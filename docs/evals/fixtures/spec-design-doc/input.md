# レビュー滞留アラート機能 設計メモ

文書種別想定: 設計書・仕様書（社内）。評価時は `review`。リズム調整は弱。平坦さの〔助言〕は適用しない。

---

近年、開発プロセスの最適化が重要視されています。
効率的な運用を実現し、品質を高め、生産性を最大化することが求められます。
考えてみてください。問題はインフラではない。レビュー待ちの可視化だ。
そこにこそ改善の本質があります。

## なぜこの機能が必要なのか？

Platform チームは、レビュー依頼から初回応答までの中央値が伸びると、
機能追加のリードタイム全体が押し上がる、という仮説のもとで対策を検討している。
本機能はゲームチェンジャーになり得る。今後に向けて、同じ認識に立つことが鍵となる。

## 動作の流れ

オペレータがダッシュボードを開き、滞留一覧を確認する。
その前に、対象リポジトリで `REVIEW.md` がリポジトリルートに存在している必要がある。
また、GitHub App「review-watch」v1.4.0 がインストール済みであること、
および Organization の webhook に `pull_request` と `pull_request_review` が含まれることが前提である。
滞留と判断された PR は、Slack の `#eng-review` に通知される。
通知先チャネルは環境変数 `ALERT_SLACK_CHANNEL` で上書きできる。
タイムゾーンは `Asia/Tokyo` 固定とする。

処理の流れは次のとおりである。

- GitHub から open な PR を取得する
- 最終レビュー催促から経過時間を計算するため、まずレビュー催促イベントを読む
- 経過が閾値を超えていれば Slack に投稿する
- 閾値はデフォルト 24 時間である。`ALERT_THRESHOLD_HOURS` で変更できる
- 取得に失敗したら最大 3 回リトライする。それでも失敗したらエラーをログに出し、その PR をスキップする

Circuit Breaker は外部 API 障害の局所化に使う。
本機能の必須構成ではないが、信頼性の文脈では言及されることがある。
外部 API 呼び出しは HTTP ではなく HTTPS を使う。

## 入出力の概要

入力は GitHub の PR 一覧である。
出力は Slack メッセージである。
誰が・どの条件で・何を出すかは、運用者がダッシュボードで確認する想定である。

滞留の定義は、レビュー依頼ラベル `needs-review` が付いたあと、
初回の approve / request_changes / comment レビューが無く、
かつ経過時間が閾値以上の PR とする。
下書き PR と `do-not-alert` ラベル付き PR は対象外とする。

## 設定項目

閾値は `ALERT_THRESHOLD_HOURS`（整数、単位は時間、デフォルト 24）で指定する。
通知先は `ALERT_SLACK_CHANNEL`（文字列、デフォルト `#eng-review`）である。
ドライランは `ALERT_DRY_RUN`（真偽、デフォルト false）で、true のときは Slack 投稿を行わずログのみとする。
バッチ間隔は 15 分固定であり、設定では変更できない。

## 例外と失敗時

GitHub API が 403 を返した場合は、権限不足としてジョブ全体を失敗させる。
個別 PR の取得失敗は、上記のとおり最大 3 回リトライのあとスキップする。
Slack API が失敗した場合は、その通知だけを失敗とし、他 PR の処理は継続する。
障害が再発する可能性があるため、ジョブ失敗時は `#eng-platform` へのページャー連携を推奨する。

一方で、注意点もあります。すべてのリポジトリが常にこの設定を守ります。
誰もが例外なく `REVIEW.md` を配置してから運用を開始します。

## おわりに

以上のように、本機能は効率化を実現し、品質を高め、可視性を最大化する。
この節で述べたとおり、本質は人とプロセスにある。

結論として、本機能の目的は、レビュー依頼後 24 時間（既定）を超えて初回応答が無い PR を
Slack に通知し、滞留を早期に解消できるようにすることである。
行為者はバッチジョブ `review-watch-worker`（毎時 0,15,30,45 分）であり、
入力は GitHub open PR、出力は Slack 通知とダッシュボード上の滞留一覧である。
前提は `REVIEW.md` の存在、GitHub App review-watch v1.4.0、所定の webhook である。
対象外は下書き PR と `do-not-alert` ラベル付き PR である。
Platform チームは 2026年9月末までに、Backend 以外のグループへの展開可否を判断する予定である。
