# 生成AI特有の日本語の癖

Claude を含む言語モデルが日本語を書くときに繰り返し出る癖をまとめる。診断時のチェックリストとして使い、該当箇所だけを直す。癖の除去を目的化して、必要な情報や丁寧さまで削らない。

英語圏の AI 定型（slop）を整理した [hardikpandya/stop-slop](https://github.com/hardikpandya/stop-slop) のパターンのうち、日本語でも同様に出るものを取り込む。英語固有の規則や、このスキルの設計方針と衝突するものは採らない（採用範囲は [design/rationale.md](../docs/design/rationale.md)）。

## 目次

1. 語彙・言い回し
2. 構造・段落
3. 表記
4. 内容の水増しと捏造
5. 検出しにくい癖

## 1. 語彙・言い回し

| 癖 | 例 | 直し方 |
|---|---|---|
| 冗長な機能表現 | 〜することができます / 〜を行います / 〜という形になります | 〜できます / 〜します |
| 空の前置き | まずは基本から確認しましょう / 詳しく見ていきます | 削除して本題から始める |
| 定型の強調 | 重要なのは〜という点です / ここでポイントとなるのが | 主張そのものを書く |
| 営業調の動詞 | 〜を実現します / 〜を可能にします / 〜の鍵となります | 何がどう変わるかを具体的に書く |
| 過剰な副詞 | 非常に / 極めて / 圧倒的に / まさに / 劇的に | 削除するか、数値・事実に置き換える |
| 英語直訳の接続 | 〜に関して / 〜という観点から / 〜を通じて | 〜は / 〜で |
| 感情的な枕 | 素晴らしいご質問ですね / 大変興味深い点です | 削除する |
| 過剰な留保 | 一般的には / 場合によっては / あくまで の連発 | 一文につき最大一つに絞る |
| 重要さの宣言だけ | 本質的には構造の問題です / 影響は甚大です / ここが最大の論点です | 何がどう構造的か、誰に何が起きるか具体を書く |
| メタな進行説明 | この節では〜を説明します / 以下で詳しく見ていきます / すでにご存じかもしれませんが | 削除して本題の文から始める |
| ビジネスジャーゴン | 深掘りする / ナビゲートする / ゲームチェンジャー / 今後に向けて | 普通の動詞・名詞に置き換える（下表） |

**ビジネスジャーゴンの置き換え**

| 避ける | 使う |
|---|---|
| 〜をナビゲートする | 対処する / 進める |
| 深掘りする / ディープダイブ | 分析する / 調べる |
| 寄り添う / リーンインする | 受け入れる / 取り組む |
| ゲームチェンジャー | （具体的な変化を書く） |
| 今後に向けて / ムービングフォワード | 次に / これから |
| 立ち返る / サーフルバック | 戻る / 再検討する |
| 同じ認識に立つ | 合意する / 揃える |
| 今日の〜環境では / 〜が求められる時代に | （時代論を削り、対象の事実から始める） |

**修正例**

- 原文: 本ツールを活用することによって、開発チームは非常に効率的にレビューを行うことが可能になります。
- 修正: 本ツールを使うと、レビューの待ち時間が短くなる。

- 原文: 重要なのは、影響が甚大だという点です。この節ではその理由を見ていきます。
- 修正: 障害時にロールバックが遅れると、復旧まで平均40分かかる。

## 2. 構造・段落

- **過剰な三項列挙**: 常に三つ並べる。三つ目が一つ目の言い換えになっていることが多い。項目間に検証できる差分がなければ、〔助言〕に留めず修正文から削除する。差分がある項目だけ残し、数を揃えるために項目を足さない。固有の事実が一つもなければ、列挙全体を削り、削除した内容を説明する。
- **言い換えだけのまとめ**: 「以上のように、〜は重要です」で終わる段落。新しい情報がなければ削除する。
- **箇条書きの濫用**: 散文で流れが説明できる内容を箇条書きに割る。因果や条件でつながる情報は文章のまま書く。並列で対等な情報だけ箇条書きにする。
- **箇条書きの不揃い**: 体言止めと文が混在する、粒度が揃っていない。項目内の形式を統一する。
- **見出しの過剰分割**: 2〜3文ごとに見出しが入る。1見出しにつき最低1段落を目安にする。
- **対句・体言止めの過剰**: 「速く、正確に、確実に。」のような装飾。技術文書では削る。
- **太字の濫用**: 一段落に複数の太字がある場合、強調が機能していない。段落あたり最大1箇所を目安にする。
- **二項対立の定型**: 「問題は X ではない。Y だ」「答えは A ではなく B」「〜ではなく、実は〜」で転換を演出する。否定側を落とし、主張側だけを直接書く。
- **否定による劇的列挙**: 「A ではない。B でもない。C だ。」と否定を重ねてから本題に入る。C を先に述べる。
- **修辞的な前振り**: 「考えてみてください」「もし〜だとしたら？」「つまりこういうことです」で洞察を予告する。前振りを削り、主張を書く。
- **偽の行為者**: 無生物に人の動詞を持たせる（「苦情が修正になる」「決断が立ち上がる」「データが物語る」「文化が変わる」）。行為する人やチームを主語にする。特定できないときは、誰の行為かが分かる書き方に変える。日本語の自然な主語省略まで能動態に直さない。
- **俯瞰ナレーター**: 「誰も設計していない」「人は〜しがちだ」「だからこうなる」と場面の外から説教する。誰が・何を・いつするかに落とす。業務文書では「あなた」への呼びかけより、主体と行為の明示を優先する。

**二項対立・否定列挙の修正例**

- 原文: 問題は技術の複雑さではない。人の複雑さだ。そこにこそ本質がある。
- 修正: 技術より、利害の食い違いの方が調整に時間がかかる。

- 原文: これは効率化ではない。学習でもない。意思決定の高速化だ。
- 修正: これは意思決定を速くするための仕組みだ。

**修辞・偽の行為者の修正例**

- 原文: 考えてみてください。データが私たちに語りかけています。文化が変わり始めているのです。
- 修正: 先週の計測では、差し戻し率が 12% から 5% に下がった。レビュー担当が指摘テンプレートを使い始めたのが要因だ。

**三項列挙の修正例**

- 原文: 本機能には次の3つのメリットがあります。1つ目は効率化です。2つ目は品質向上です。3つ目は生産性の最大化です。
- 修正: （原文に検証できる差分がないため削除。何がどう変わるかの具体が必要なら確認する）

- 原文: 本機能はレビュー待ち時間を短縮し、差し戻し率を下げ、手戻りを減らす。
- 修正: 本機能はレビュー待ち時間を短縮する。差し戻し率の低下も確認されている。
- 注: 「手戻りを減らす」が差し戻し率低下の言い換えなら落とす。計測できる項目だけ残す。

**演出短文・全称の修正例**

- 原文: 速い。正確。確実。それだけだ。それが全てだ。
- 修正: （対象が無い性質語の連打のため削除。何が速いのかを書き足すか、削除でよいか確認する）

- 原文: すべてのチームが常にこの手順を守ります。誰もが例外なくレビューを完了してからマージします。
- 修正: （変更せず）〔指摘〕「すべて」「常に」「誰もが例外なく」の根拠が原文にない。適用範囲と例外を明示するか、全称を外す。

## 3. 表記

- 半角英数字と日本語の間のスペースの有無を、文書内で統一する
- 括弧を全角と半角で混在させない
- 感嘆符、絵文字、「〜」の多用を避ける（媒体が求める場合を除く）
- 敬体（ですます）と常体（である）を混在させない。混在が意図的な文体である場合は保持する
- 三点リーダーは「…」を使い、「...」と混在させない
- 箇条書き末尾の句点の有無を統一する

## 4. 内容の水増しと捏造

生成AIの出力で最も害が大きい。読みやすさより優先して確認する。

- **数値の捏造**: 原文にない「30%改善」「3倍高速」などを補わない。出典がなければ書かない
- **具体例の捏造**: 説明を補強するための架空の事例や企業名を足さない
- **一般論の水増し**: 「近年、〜が注目されています」のような、誰でも書ける導入を足さない
- **根拠のない断定**: 原文が可能性・推奨で書いている内容を、断定・義務に変えない
- **削除による意味の欠落**: 短くする過程で、条件・例外・前提が落ちていないか照合する
- **極端な全称**: 「すべて」「常に」「決して」「誰もが」で権威づけする。原文に範囲の根拠（計測、規程、例外条件）がなければ〔指摘〕とし、修正文で勝手に狭めない。残す場合は確認事項にする。重複した全称の言い換えだけをまとめて済ませない

## 5. 検出しにくい癖

構造上は正しく見えるが、読むと内容が薄い状態。

- **同義反復の段落**: 前段落と主張が同じで、語彙だけ変えている
- **主語の消失**: 「〜が求められます」「〜が重要とされています」で、誰がそう求めているか不明
- **抽象度の高止まり**: 「最適化」「効率化」「活用」だけで、何をどうするかが書かれていない
- **平坦な密度**: 語彙は整っているが、全段落が同じ抽象度・同じ調子で続き、具体への着地がない。読み進める負荷が下がらない。演出（問い・緊張・短長の交互）を足して取り繕わない。段落を分けるか、原文にある具体（数値・手順・例）を主張の直後に置く。解説記事での〔助言〕の扱いは [genre-guidance.md](genre-guidance.md) を参照する
- **バランス取りの定型**: 「一方で、注意点もあります」と書いて、実質的な注意点を挙げない。直後が根拠のない全称や空の留保だけなら、接続句ごと削る。全称自体の扱いは「極端な全称」に従う
- **数値の方向の取り違え**: 「離脱率が37%まで向上」のように、改善・悪化の向きと語が食い違う。数値と評価語の向きが一致しているか照合する（依頼範囲の扱いは SKILL.md「依頼範囲を超えない」を参照）
- **許可を与える締め**: 「それでいいのです」「完璧である必要はありません」など、読み手への不要な許可。論旨に必要なら残し、定型なら削る
- **演出的な短文連打**: 「速い。正確。それだけだ。」のように断片を畳む。性質語だけの断片で、何がそうなのか（対象名詞）が無ければ、形を整えて残さず削除候補にする。対象が明示できるときだけ普通の文に戻す。エッセイなど意図的な文体は [genre-guidance.md](genre-guidance.md) に従う

**修正例**

- 原文: 近年、AI開発の分野では、開発プロセスの最適化が重要視されています。効率的な運用を実現するためには、適切なツールの活用が求められます。
- 修正: （原文に固有の情報がないため、全削除して本題から始める。削除の可否をユーザーに確認する）

- 原文: レビュー待ちは開発全体の速度に影響する。プロセスの見直しが生産性を左右する。適切な運用設計が鍵となる。計測では初回応答の中央値が18時間から6時間に短縮した。
- 修正: レビュー待ちは開発全体の速度に影響する。計測では、初回応答の中央値が18時間から6時間に短縮した。
- 注: 抽象の連打を削り、具体の数値を主張の直後へ着地させた。短長を交互にするための文の分割はしていない。

- 原文: 一方で、注意点もあります。すべてのチームが常にこの手順を守ります。
- 修正: （「一方で、注意点もあります」は削除。全称文は根拠がなければ〔指摘〕とし、狭めず残すか確認する）
